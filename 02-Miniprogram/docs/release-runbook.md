# 小程序开发版发布与排查

## 入口和边界

从 [项目 README](../README.md) 确认当前源码、上传记录与审核语。代码推送、客户端上传、微信审核、正式发布是四个独立状态；只有实际回执能证明上传，审核和正式发布由负责人执行。历史发布记录不改写。

## 打包前

1. 核对工作树与远端，保留其他任务改动；固定准备上传的源码提交。
2. 在 `02-Miniprogram` 运行 `node scripts/sync-reviewed-funding.mjs`，核对线上清单与审核源。若线上正处于切版、返回旧模型或异常数量，不能直接覆盖已审核基线；先确认服务器发布回执，再重读版本与索引。
3. 运行 `npm run verify`，检查生成差异属于本次已接受更新。1.2.5 的 `cards` 是主体卡，`events` 是独立融资事件，二者数量不可互换；确认历史轮次和旧 ID 别名仍保留。
   1.2.6 起，服务端精选部署后运行 `npm run sync:featured` 固定已发布精选快照。线上缺少有效 selection 时停止打包，不能以最新三条充当审核精选。
4. `package.json`、`miniprogram/utils/analytics.js` 和 CLI 上传版本一致；末位达到 9 后进位，不使用 1.1.10。
5. 将接受的改动提交并推送，再从精确提交 `git archive` 到私有发布目录。逐文件核对 Git blob，避免上传未提交代码。私有预览、日志和回执不进入公开仓库。

## 上传与记录

使用本机微信开发者工具 CLI 的 `upload --project <归档工程目录> --version <版本> --desc <审核摘要> --info-output <私有回执文件>`。CLI 的退出码有时为 0 但正文包含 Upload 错误，必须确认日志出现 `√ upload`，再记录提交、版本、包体字节数和验证边界。

上传后补写 `docs/releases/<版本>/README.md`，与 `docs/REVIEW-<版本>.md` 互相引用。文档提交不会改变此前上传包；不要把后补文档提交误记为包体源码。

## Windows 迁移缓存 EEXIST

本机开发者工具用户目录有迁移链接。若报错指向 `WeappCache/skeletonCache/<hash>` 或 `WeappCache/WeappCompileCache/<hash>`：

- 先查看报错路径及 Windows 链接的实际目标，只在已核验的物理缓存根目录补建报错指定的缺失子目录，然后重试。
- 不删除整个开发者工具用户目录、登录状态或项目缓存；不复制其他版本的哈希目录作为通用修复。
- 保存成功回执。终端显示 upload 错误时不得仅凭退出码认定上传成功。

## 昵称与权限核验

- 注册：选择头像，点选微信昵称，结束输入并通过原生校验后授权手机号。测试快捷填入无 input 事件、旧值替换、校验失败／超时、取消授权及重复提交。
- 手机号授权不返回昵称，不把 wxid 当作真实姓名。服务端已确认昵称优先于客户端草稿。
- 真机昵称选择需要独立验收。测试通过或开发者工具编译成功不能代替真机证据。
- 已登录用户档案加载时不提前展示注册门槛；社群阅读沿用统一权益，本人资料写入仍校验绑定身份。

## 临时产物清理

上传源码保存在 Git，成功日志、回执与版本归档需保留。仅当上传记录、源码提交和展开目录均已核对时，临时传输 tar 可以删除并按原提交重建。数据库备份、运营授权流水、身份匹配审计以及其他任务工作树不属于普通打包缓存。
