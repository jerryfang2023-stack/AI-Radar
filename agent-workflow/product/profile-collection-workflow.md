# 档案补采执行流程

适用于机构背景、个人投资者和独立人物档案。事实字段及发布门槛仍遵循 [Public Entity Profiles V1](public-entity-profiles-v1-contract.md)。任务管理使用 `npm run profiles:queue -- <命令>`，要求 Node 22.13+ 或 Node 24；不启动额外定时任务，不自动调用付费模型。

## 共享状态与隔离

各窗口使用独立源码工作目录和同一个私有队列。状态目录按 `--state-dir`、`GUANLAN_PROFILE_STATE_DIR`、本地 `.profile-collection.json` 的 `stateDir`、Git 主工作目录的同名共享绑定、已配置私有证据根下的 `runtime/profile-collection` 顺序解析。配置和正文不进入公共 Git。第一次初始化时确认所有工作者使用相同目录，不能每个工作目录各建一个队列。

运行 `seed` 导入所有未达到 `coverage_status=researched` 的机构/人物档案，以及身份待核和缺少来源证据的主体；不得再按旧 `investor_kind` 白名单漏掉已有主体档案。已确认身份、有官网、融资关联多的研究对象排前；身份核验作为独立 lane，默认领取研究对象。重复初始化保留已领取、候选和已验收成果；如果已整合档案仍出现在待补采 backlog，`seed` 会把该任务重新排队并保留当前事实档案。`status` / `report` 会把 backlog 与队列对账，显示机构、人物/个人投资者、待确认主体/缺少证据三类数量，各类队列状态、漏入队 ID 和“队列已整合但 backlog 仍待补采”的 ID；发现漏项后执行 `seed`，不要手工改 SQLite。任务日志表示处理阶段，不等同于持续推理工时；整合完成仍是待提交发布。

## 采集与审核

1. 每个工作者运行 `claim --worker=<窗口名> --limit=10 --output=<私有领取文件>`，然后在该工作窗口的独立终端运行 `watch --input=<同一领取文件>`。watcher 会立即续期，并默认每 5 分钟续期；任务完成或阻塞后，它检测到凭证不再活动会自动结束，也可在终端按 Ctrl+C。领取凭证默认有效 15 分钟，续期沿用该领取的租约时长；自定义较短租约时，watch 间隔必须不超过租约的三分之一。旧凭证不能续领或覆盖另一窗口的结果。手动操作仍可用 `heartbeat --key=<集合:ID> --token=<凭证>` 或 `heartbeat --input=<领取JSON>`。两个窗口领取时必须使用不同窗口名和私有领取文件。
   双窗口启动时先看 `status` 的 backlog/lane 数量，有待办时可分别领 `research` 和 `identity`；某个 lane 用尽后再切到剩余待办较多的 lane。即使两边临时领同一 lane，共享队列仍会原子分配不同 ID。
2. 领取后先查已有正文，收集需要的官网 URL；`capture --input=<URL数组JSON> --concurrency=6` 只抓缺失/过期正文，单网站最多 2 个请求。URL 去掉 fragment；参数保留，避免合并不同内容页。24 小时缓存跨任务、跨窗口复用；相同 URL 的并发抓取也只有一位持有者。HTTP/浏览器失败记录并转疑难队列，不反复拖住整批。
3. 网络正文不足或需人工浏览时，使用 `import-capture --input=<元数据JSON> --body=<原文文件>`；元数据必须包括 HTTPS `url`、`title` 和真实 `captured_at`，不得用导入时间冒充采集时间。原文文件放私有目录，`evidence/<SHA256>.txt` 保留不可变正文；联网/浏览器仍需核对来源主体。
4. 根据原文生成符合 schema 的单档案 JSON，保留源 ID、64 位正文哈希和摘录哈希。`complete --key=<集合:ID> --token=<凭证> --input=<档案JSON>` 校验 schema、明确身份/类型、真实摘录、字段来源和核验日期，仅生成候选。每条摘录必须是已缓存正文的连续片段；不接受搜索摘要作为档案证据。已有融资证据无需改写，覆盖生成器会补回保留。
5. 负责验收的编辑核对简介和每个字段的归属、口径、日期及隐私范围，再运行 `approve --key=<集合:ID> --reviewer=<验收者>`。程序不能判断事实解读是否正确，不得仅因机器校验通过就跳过内容审核。不同档案间复用来源，不复用未经核对的同名人物推断。候选尚未验收时若需调整内容，生成完整修订档案并运行 `revise --key=<集合:ID> --input=<档案JSON>` 更新候选后再验收；不得直接改写共享 SQLite。已验收候选需先 `reopen`，再 `revise` 并重新 `approve`。
6. 无法确认身份/遇到复杂冲突时运行 `fail --key=... --token=... --reason=<具体原因>`；暂时网络故障可加 `--retry=true`。自动重试最多 3 次后阻塞，处理原因后才用 `retry --key=...` 显式恢复。手工研究默认单对象 8 分钟，超过后记录缺口并转阻塞；不得为凑数量降低证据要求。

## 按批整合和恢复

`integrate --batch-size=30` 累积 30 条已审核档案再执行，最多允许 50 条；收尾时明确使用 `--flush=true` 整合不足一批的成果。只有整合者写事实源和生成投影。它检查领取以来的事实源变化，发生并发改动时保留两份成果并要求重新核对，不覆盖另一窗口的新内容。先检查差异，再用 `reopen --key=... --reason=<复核原因>` 退回候选、更新比较基线，重新审核后 `approve`。正在恢复的整合计划中不得改动候选。

并行窗口分别准备发布时，为每个窗口使用不同的 `approve --reviewer=<窗口标识>`，并在整合时指定相同的 `integrate --reviewer=<窗口标识>`；此筛选只整合该验收人的档案。未完成的整合计划绑定验收人，只能由同一验收人恢复。省略 `--reviewer` 时仍按共享队列中最早验收的档案整合。所有窗口共用整合锁和 Portal 发布锁：资料采集可并行，事实源整合、Git 合并和线上发布要串行推进；开始下一次发布前确认上一次的提交、部署回执及网站/小程序数据哈希。如果发布客户端在 SSH 清理阶段超时，先核对远端回执和锁持有者状态，再决定是否恢复，不能仅凭本地退出码重发或清除未知锁。

24 小时过期只影响抓取复用和初次提交。候选已绑定 URL、正文哈希与采集记录；审核和整合继续核对不可变原文，网站后来变化或排队超过一天都不会强制重采。正文丢失或哈希不符仍会阻止整合。

整合只执行 coverage → profile 投影 → 档案门禁 → 投资方门禁，不执行全站 `sync:data-center`。无变化的 JSON 不重新写盘。证据进入现有私有证据归档；整合命令从当前工作树或 Git 主工作目录解析同一备份路径，隔离 worktree 无需复制 `.evidence-backup.json`。生成失败保留已验收事实、候选和阶段计划，再次 `integrate` 从失败构建恢复，不重采上游。`integration.json` 绑定原工作目录，跨目录恢复须先核对源与计划。归档使用既有证据写入器，安排整合窗口时避免与另一个证据归档写入任务同时写同一 catalog。

整合后的事实及投影应一起审查、提交、合并；可以每两小时或 30—50 条汇总发布。发布由独立干净工作目录从固定源码提交生成，执行现有 Pages → Portal 流程，并分别核对网站与小程序档案 ID、数量、数据版本及回执。客户端接入/微信正式发布仍需单独确认，不能用后台数据同步代替。

## 对任务进展的报告

每批分别记录新档案、存量完善、已验收、已整合、已发布和阻塞数；人物包括投资方集合中的个人投资者，按 ID 统计，跨集合去重另报。候选数、网页数、生成文件数均不能充当可发布档案数。

加速目标先用相同难度样本测量。确定性回放检查证据复用、并发上限和每批构建次数；真实采集按至少 30 个同难度对象比较验收档案/小时、验收率和单条成本。代码回放成功不能作为真实采集提速倍数。
